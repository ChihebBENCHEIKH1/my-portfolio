Fixing Hugging Face filesystem caching

By Chiheb Ben Cheikh · Founder, BiancoToro Technologies · PR status checked 14 November 2026

A bucket folder with 28 files could appear to contain just one after listing a single file. The files were still present; the cached directory listing was wrong.

The problem

HfFileSystem._ls_tree appended entries to its parent directory’s cached listing while walking a tree. Repeated listings could accumulate duplicates, a refresh could retain deleted entries, and an interrupted walk could leave a partial result cached.

There was also a bucket-specific case: listing one file could cache that entry alone as its parent folder’s listing. Later checks could incorrectly report that sibling files did not exist.

The observed behavior

The reproduction recorded in the pull request compares the cached folder with a fresh filesystem instance:

Before the fix:
ls(bucket folder) after ls() on one file: 1 vs 28 on a fresh instance
exists(sibling file): False

With the fix:
ls(bucket folder) after ls() on one file: 28 vs 28 on a fresh instance
exists(sibling file): True

My contribution

I changed the listing logic to build the directory listings during the walk, then store them after the listing completes. The completed listings replace the previous cache entries instead of appending to them.

The entry matching the requested file path is not cached as its parent folder’s listing. This handles the bucket response without treating a single file as a complete directory.

Verification and scope

The pull request includes offline regression tests for repeated folder listings, an interrupted listing, and listing a bucket file before its folder. Its description records the before-and-after reproduction and the checks run for that contribution.

I contributed this fix to the open-source huggingface_hub project. Pull request #5099 is merged; its description contains the reproduction and verification notes.

The engineering lesson

A directory cache represents a complete snapshot. Updating it incrementally can expose an incomplete result as authoritative state. The fix aligns the cache update with the point at which the walk has actually completed.
